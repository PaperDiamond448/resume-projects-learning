# LFM copy-correlation: MATLAB -> C -> STM32F407VGT6

## Status

**Algorithm core: ported and numerically validated.** `algo/lfm_algo.c` is a
line-by-line C translation of `lfm2_2.m` + `detpart.m` (the copy-correlation
matched filter, double-threshold peak detector, and detpart peak-selection
logic). It was run on the PC against the real channel-1 recording
(`signal_all_35_50.mat`, num=1) via `host_test/main_host.c`, and the output
was compared field-by-field against the original `result.txt`:

```
193/193 data rows matched.
Delay   : identical to 4 decimal places (0.1 ms) on every row
Wid     : identical on every row
InOutRatio : identical on every row
Amp     : max difference 0.0001 (float32 vs MATLAB double rounding noise)
```

So the ported logic is confirmed correct, not just "plausible." One real bug
was caught and fixed during validation: raw ADC samples are unsigned 0..65535
codes, and an early version cast them to a *signed* 16-bit type, which wrapped
~48% of samples negative and silently corrupted every downstream stage. See
the comment above `PP_1` in `lfm_algo.c` if you're porting other pieces of
this codebase and see a similar cast.

**Hardware side: single-channel bring-up written, not yet build-tested.**
`stm32/Core/Src/main.c` wires ADC1 + DMA2 + TIM3 + USART1 around the *same*
`lfm_algo.c`/`lfm_algo.h` files (no fork -- one algorithm source, two
front-ends). It has not been compiled yet because this machine's Keil
install has the STM32F1xx device pack but not STM32F4xx -- see **Setup**
below for the two ways to fix that.

## Layout

```
firmware/
  algo/            portable C core -- no STM32/HAL dependency
    lfm_algo.h/.c    the ported algorithm (coeffs, per-packet processing, peak selection)
    fft_complex.h/.c  standalone radix-2 complex FFT (verified against numpy)
  host_test/       PC-side validation harness
    prepare_input.py  exports channel 1 from the .mat into raw binary (run once)
    main_host.c       drives lfm_algo.c block-by-block like lfm2_2.m, writes result_c.txt
    main_host.exe     already built (TDM-GCC at D:\Dev-Cpp\TDM-GCC-64)
  stm32/           STM32F407VGT6 firmware
    Core/Inc/main.h
    Core/Src/main.c   ADC1+DMA2+TIM3+USART1 glue around lfm_algo.c
```

## Setting up the Keil project (what you need to do)

Your Keil (`H:\keil5`) has the CMSIS core pack but not the F4 device pack yet
(it has `Keil.STM32F1xx_DFP`, used by your other project's F103 experiments,
but not `Keil.STM32F4xx_DFP`). Two ways to get a working project, pick one:

**Option A -- New uVision Project wizard (recommended, ~2 minutes):**
1. Project -> New uVision Project -> save it anywhere under `firmware/stm32/`.
2. Device search: `STM32F407VG`. If it's not in the list, Keil will offer to
   fetch the pack automatically (needs internet) -- accept it. If that fails,
   open Project -> Manage -> Pack Installer, search `STM32F4xx_DFP`, install
   version 3.1.1 or newer, then retry device selection.
3. When asked to copy the startup file to the project folder, say **Yes**.
4. Project -> Manage -> Run-Time Environment. Under **Device**, tick:
   `Startup`, `STM32Cube HAL` is *not* needed -- this firmware uses the older
   StdPeriph API instead (`Device > StdPeriph Drivers`): tick `RCC`, `GPIO`,
   `DMA`, `ADC`, `TIM`, `USART`, `Framework`. Keil auto-generates
   `stm32f4xx_conf.h` and adds the matching driver `.c` files -- you don't
   need to hand-copy StdPeriph source.
5. Add to the project (existing group, or a new "algo" group):
   `algo/lfm_algo.c`, `algo/fft_complex.c`, `stm32/Core/Src/main.c`.
6. Add `algo/` and `stm32/Core/Inc/` to the include path
   (Project -> Options for Target -> C/C++ -> Include Paths).
7. Target memory (Options for Target -> Target tab) for **STM32F407VG**
   specifically (not F427 -- it has less RAM, see the RAM budget note
   below): IROM `0x08000000` size `0x100000` (1MB), IRAM `0x20000000` size
   `0x20000` (128KB main SRAM). Leave CCM (`0x10000000`, 64KB) unmapped as
   IRAM2 unless you explicitly place something there -- DMA cannot reach it.
8. Build (F7). Send me whatever error list comes back and I'll fix it from
   here -- I translated the algorithm against the StdPeriph API from
   documentation/memory since I don't have a compiler for this target in my
   own environment, so the first build is where real typos will surface.

**Option B -- headless via STM32CubeMX (H:\stm32):** CubeMX can generate an
MDK-ARM project with pins/clock/ADC/DMA/TIM already configured through its
GUI, which sidesteps hand-configuring StdPeriph calls in code entirely (trade
-off: you'd get HAL-style generated init code instead of the StdPeriph calls
in the current `main.c`, so this path needs adapting `main.c` to call into
CubeMX-generated `MX_*_Init()` functions instead). Tell me if you'd rather go
this way and I'll restructure `main.c` for it.

## Architecture notes / why it's built this way

- **One algorithm source, two front-ends.** `lfm_algo.c` doesn't know whether
  its `uint16_t` samples came from a `.mat` file or an ADC. The host harness
  and the STM32 firmware both call the exact same `lfm_process_packet()`.
  If you ever suspect a bug, re-run `host_test` first -- it's the fast,
  ground-truth-checked path, versus rebuilding+flashing to check the same
  logic on hardware.
- **Packet-level API, not streaming.** `lfm_process_packet()` takes a whole
  16384-sample packet at once (matching `lfm2_2.m`'s `block_num` loop). On
  the STM32 side, `main.c` accumulates 8 DMA-delivered 2048-sample
  sub-blocks into a staging buffer before calling it. This kept the port
  mechanically checkable against the .m source, at a real RAM cost -- see
  next point.
- **RAM budget is tight for 1 channel, does not fit for 3 as-is.** Rough
  tally for one channel: `lfm_channel_state_t` (~32KB) + `lfm_algo.c`'s
  internal scratch buffers (~84KB, mostly the 16384-sample staging copy and
  the FIR/FFT scratch) + the DMA ping-pong + packet buffers in `main.c`
  (~40KB) is already ~156KB out of the STM32F407VG's 192KB SRAM (128KB main
  + 64KB CCM, and CCM is **not** DMA-reachable -- don't move DMA buffers
  there). Tripling that for all 3 hydrophone channels does not fit. Before
  wiring up channels 2 and 3, restructure `lfm_process_packet` to work at
  the natural 2048-sample sub-block granularity (the `cnt2` loop already
  processes one sub-block at a time internally) instead of staging a full
  16384-sample packet first -- that alone removes the biggest buffers.
- **No sync detection on the hardware path yet.** `lfm2_2.m` knows exactly
  which sample is the sync pulse because that information was embedded in
  the recording (`signal_all(n).syn`) for offline analysis. Real hardware
  doesn't have that a priori. `main.c` currently always passes `has_sync=0`,
  so `lfm_channel_force_select()` (declared in `lfm_algo.h`) needs to be
  called on whatever real trigger you'll use -- a detected sync condition,
  or a scheduled call tied to the known ping repetition period.
- **No attitude/position solve exists anywhere in this codebase yet**
  (neither the original MATLAB nor this port) -- everything here reproduces
  `result.txt`: per-channel candidate delay/amplitude peaks. Turning 3
  channels' delays into an actual attitude/bearing is a separate, smaller
  piece of geometry math (a few trig/matrix operations) that still needs to
  be written once you're ready for it.
- **Clock note:** `main.c`'s `SystemClock_Config()` assumes an 8MHz HSE
  crystal -> 168MHz SYSCLK. 156250 Hz doesn't divide evenly out of that (or
  any standard STM32F4 PLL output), so `TIM3`'s ARR is tuned to the closest
  achievable rate (156133.8 Hz, ~0.07% low) -- negligible in practice, but
  change `ADC_TIM_ARR` if you retune `SystemClock_Config` or your board uses
  a different crystal.
